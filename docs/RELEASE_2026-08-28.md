# Functional synchronization — 28 August 2026

This release moves the public NFRP boundary from 25 to 28 August 2026. The working transport ERP remains the sole functional reference; NFRP receives a sanitized implementation with synthetic identities, providers, fixtures and seed data.

## Included in this synchronization

### Registries open on the list, with instant search

Drivers, motor vehicles, trailers, customers, other entities and external owners no longer put a creation form beside the list. Each menu entry now opens the full list with a search field at the top and a create button in the page header, leading to a dedicated `.../new` page that also receives the validation errors of its server action.

Search runs in the browser over the rows already rendered, so results narrow while typing without a network round trip. It ignores accents, case and punctuation and requires every typed term in any order, so `zz 575 zz` matches `ZZ575ZZ` and `575` is enough to reach the plate. The counter always states how many rows the search is hiding. This applies to these short registries only: registers that grow without bound keep server-side pagination.

### The working unit: driver, motor vehicle, trailer

The three fleet registries now show each other. Lists carry the linked columns — driver lists show the motor vehicle and the trailer, motor-vehicle lists show the driver and the trailer, trailer lists show the tractor unit and the driver — and all three detail pages open with a `Complesso di oggi` panel whose entries link to the other two records.

No link is inferred. The driver comes only from the dated tractor-driver assignment that covers today in the `Europe/Rome` calendar day, through a single shared function used by both lists and detail pages, and the trailer comes from the recorded pairing. When a link is missing the application says so and points at the place where it is configured. A trailer has no driver of its own: it shows the driver of the paired motor vehicle, and when a tractor unit is paired with more than one trailer every plate is listed instead of picking one.

### Road fines read from PDF

`/fines/import` and the `Verbali` entry in `Acquisisci` accept several notice PDFs at once. The parser proposes only the fields the document actually proves and every file becomes a `TO_REVIEW` draft that stays out of the cost center, with the PDF attached, a SHA-256 fingerprint and explicit review warnings. Re-sending the same file is recognized as a duplicate; a different PDF of the same notice is kept as an additional attachment. Leaving `Da controllare` requires the four mandatory fields — enforced by a database constraint — plus an explicit confirmation that the draft was checked.

### Container waybills from photographs, and a form that follows the operational sheet

Waybill acquisition accepts JPG, PNG and WebP in addition to PDF, validated by binary signature rather than by declared extension. Image OCR runs sequentially, because running it in parallel made a real photograph exceed the timeout and come back unreadable.

Acquisition creates no master data: it links existing drivers, vehicles and customers and leaves everything `PENDING`. The extraction now also proposes the stop read from a photograph (address, postal code, city, province), the shipping-company reference, the terminals without OCR noise and the container type in the shape of the form dropdown, with the stop type following what the document declares.

The container trip form follows the order of the operational spreadsheet — trip sequence, return base, extensible container type with ADR/reefer detail, additional cost — and shows real kilometres, deviation and euro per kilometre recalculated live without storing them. The colour legend of that spreadsheet is an implementation specification, not decoration: its yellow fields are real dropdowns with an `Altro` option, and its green values use the sheet's own wording.

## Public-data boundary

The repository contains no production database, uploaded document, backup, `.env`, credential, private endpoint, company logo or company record. This synchronization replaced every real identity introduced by the transferred code with synthetic equivalents: the carrier name became `NFRP SRL`, the driver name and plate of a photographed waybill became `ANDREA VERDI` and `ZZ104ZZ`, a real consignee became `CAMPIONE PELLETTERIA`, and the plate used by the registry-search tests became `ZZ575ZZ`. Two personal names left in the previous public fixtures were replaced as well. The complete Prisma schema and all 38 additive migrations are present because they are program structure, not company data.

## What parity does not mean

This is behavioral and schema parity for the identified transport workflows, not a byte-for-byte export of a private deployment. Public branding, sample identities, provider names and document signatures intentionally differ. Production infrastructure, operational data and private backup procedures remain outside this repository.

Specifically not transferred, because they need private material: the OCR regression runs against real notice and waybill samples, the scripts that drive those samples through the review queue, and the operational installation, backup and mirror procedures. The road-fine parser and the photographed-waybill extraction are therefore published with synthetic fixtures only: their behaviour on the real documents was verified in the private deployment and is not reproducible from this repository. No route-by-route screenshot matrix or formal real-operator usability study was produced for this release.
